# superpowers:writing-plans vs writing-codes？

superpowers 的 writing-plans，究竟是在写文档，还是在写代码？

观察到：superpowers:writing-plans编写的实施计划文档，包含大量大段的详细实现代码，计划冗长而死板，内容动则上千行。代码提前写死，一是如果代码不正确则错误传导并累积，二是非常耗费token额度。

先给结论：**`superpowers:writing-plans` 生成大量详细实现代码，符合它自身的设计目标，但不应被视为通用最佳实践。** 更准确地说，它更像是一套偏“智能体可执行规格”（Agent-executable spec）的强约束工作流，而不是传统技术设计文档（Technical Design Document, TDDoc）。在实际工程中，更稳妥的做法是：**计划文档写清目标、架构、文件路径、接口契约、测试与验收；只在关键、易误解、强约束处放小段代码或小 diff；大段完整实现应进入代码仓库和 PR，而不是计划文档。**

Superpowers 官方 `writing-plans` 的确把要求写得很细：它要求在写代码前，基于已有规格生成实施计划；每个任务拆成 2–5 分钟步骤；先写失败测试、运行测试、写最小实现，再验证并提交；并且在 “No Placeholders” 和 “Remember” 部分明确要求“代码步骤必须给代码块”“每个改代码步骤要展示代码”“完整代码”。因此，如果你看到它生成很多代码，这并不是异常，而是这个 skill 的原始指令所导致的结果。([GitHub][1])

但从传统软件设计文档角度看，这种做法通常偏重。Google 风格的设计文档强调“高层实现策略、关键设计决策和 trade-off（权衡）”，并明确建议设计文档很少放代码或伪代码，除非是在描述新颖算法；API 或 schema（模式定义）也不应完整复制进去，因为冗长、细节无关且容易过时。([industrialempathy.com][2]) Atlassian 对软件设计文档的推荐结构也是架构、数据设计、接口设计、组件职责、假设依赖、术语表、评审与维护等，而不是把完整实现代码塞进文档。([Atlassian][3])

OpenAI 的 Codex（代码智能体）实践更接近一个折中方案：复杂任务应先规划，规划要包含目标、上下文、约束和完成条件（done when）；长期任务可以使用 `PLANS.md` / ExecPlan（执行计划），但官方模板强调“自包含、可验证、活文档”，并建议当需要包含 patch（补丁）时，优先用文件级小 diff 或小片段，而不是大块代码 blob（大段代码块）。([OpenAI 开发者][4]) ([OpenAI 开发者][5])

因此，判断标准可以更简单：**少量代码片段合理，大量完整实现代码通常不合理。** 合理的代码内容包括：接口签名（interface signature）、关键数据结构、测试样例、迁移脚本的关键步骤、复杂算法伪代码、容易被 agent 写错的边界处理，以及需要严格保持一致的协议/schema 摘要。相反，整文件级业务逻辑、重复样板代码、普通 CRUD（增删改查）、完整组件实现、可由测试和接口约束自然推导出的代码，都不应大段写进计划文档。

更推荐的分层方式是：

| 层级                   | 主要内容                     | 是否放大段代码  |
| -------------------- | ------------------------ | -------- |
| 规格文档（Spec）           | 需求、目标、非目标、用户可见行为、约束      | 不放       |
| 设计文档（Design Doc）     | 架构、方案对比、关键权衡、风险、接口草图     | 极少放      |
| 执行计划（Execution Plan） | 任务拆分、文件路径、测试、验收命令、关键代码片段 | 放小段，不放大块 |
| PR / diff            | 真正实现代码、测试代码、文档变更         | 放完整代码    |
| 运行日志 / 复盘            | 验证结果、失败修复、决策记录           | 不放完整代码   |

Superpowers 当前还面临一个很现实的问题：计划文档过长会推高 token 成本。项目 issue 里已有用户反馈：一个 48k 字符的单文件计划，在执行过程中可能被反复读取，造成上下文和 token 浪费；该 issue 也提到，把单体 plan 拆成 `overview.md` 和每个 task 独立文件会更高效。([GitHub][6]) 这进一步说明：即使在 agent 工作流里，**“完整、可执行”也不等于“把代码堆进一个巨型 Markdown 文件”。**

最佳实践建议如下：

第一，保留 `writing-plans` 的优点：明确目标、精确文件路径、TDD（测试驱动开发）、验收命令、预期输出、频繁小提交。Claude Code 和 Codex 官方文档都强调复杂任务要先 plan（规划），并通过测试、lint（静态检查）、typecheck（类型检查）、build（构建）等验证目标减少返工。([Claude API Docs][7]) ([Claude API Docs][8]) ([OpenAI 开发者][9])

第二，削弱它“每步完整代码”的倾向。把完整实现改成“意图 + 约束 + 接口 + 测试 + 小片段”。例如不要写 200 行函数实现，而写：修改 `src/foo/bar.ts` 中 `parseX()`；保持现有错误类型；新增 `ParseResult`；边界条件见测试；关键分支示例代码如下。这样 agent 仍有足够指导，但不会被计划里的旧代码牵着走。

第三，把计划切成小文件。对超过 5–8 个任务或超过约 10–20 页的计划，建议结构改成：

```text
docs/plans/2026-06-10-feature-x/
  overview.md          # 目标、架构、任务索引、全局约束
  task-01-tests.md     # 当前任务的测试与验收
  task-02-api.md       # 接口与最小实现
  task-03-migration.md
  status.md            # 进度、决策日志、发现与复盘
```

第四，让代码通过 PR（Pull Request，拉取请求）被审查，而不是通过计划文档被审查。GitHub 建议 PR 小而聚焦，说明目的、改了什么、额外上下文和审查顺序；Google Code Review 指南也强调小 CL（Change List，变更列表）更快、更彻底、更不易引入 bug，通常一个 CL 应是一个自包含变更，并包含相关测试。([GitHub Docs][10]) ([google.github.io][11])

可以给 `superpowers:writing-plans` 或项目级 `CLAUDE.md / AGENTS.md` 加一条约束：

```md
When creating implementation plans, do not include large full-file implementations.
Prefer concise, self-contained guidance: exact file paths, public interfaces, function signatures, failing tests, acceptance criteria, validation commands, and small code snippets only where ambiguity is high.
If a code block exceeds ~40 lines or repeats ordinary implementation logic, replace it with behavioral requirements, invariants, and tests.
For long plans, split into overview.md plus one file per task.
The actual implementation belongs in code diffs and PRs, not in the plan.
```

最终结论：**Superpowers 这样写“有其 agent 工程逻辑”，但整体仍偏激进。对开发者来说，更合理的实践应是“可执行计划 + 最小必要代码片段 + 强验证闭环”，而不是“大段实现代码计划书”。** 计划的价值在于减少歧义、锁定约束和验收标准；代码的价值则应在 repo、测试和 PR 中体现。
