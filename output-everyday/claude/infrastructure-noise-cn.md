# 量化智能体编程评测中的基础设施噪声

基础设施配置可以使智能体编程基准测试的结果波动几个百分点——有时甚至超过排行榜上顶级模型之间的差距。

SWE-bench 和 Terminal-Bench 等智能体编程基准测试通常用于比较前沿模型的软件工程能力——排行榜上的顶级名次往往只相差几个百分点。这些分数常被视为模型相对能力的精确测量，并日益影响模型部署决策。然而，我们发现仅基础设施配置就能产生超出这些差距的差异。在内部实验中，Terminal-Bench 2.0 上资源配置最充足与最紧张之间的差距达到 6 个百分点（p < 0.01）。

静态基准测试直接对模型输出评分——运行时环境不影响结果。智能体编程评测则不同：模型获得一个完整的环境，在其中编写程序、运行测试、安装依赖，并在多轮交互中迭代。运行时不再是被动的容器，而是问题解决过程的组成部分。两个拥有不同资源预算和时间限制的智能体实际上在参加不同的测试。

评测开发者已开始关注这一问题。例如，Terminal-Bench 2.0 在其最新的 2.0 版本中针对每个任务指定了推荐的 CPU 和内存配置。然而，指定资源并不等同于一致地强制执行。此外，我们发现强制执行方法实际上会改变基准测试最终测量的内容。

## 我们是如何发现这个问题的

我们在 Google Kubernetes Engine 集群上运行 Terminal-Bench 2.0。在校准设置时，我们注意到分数与基准测试的官方排行榜不匹配，基础设施错误率高得惊人：多达 6% 的任务因 Pod 错误而失败，其中大多数与模型解决任务的能力无关。

分数差异归结于强制执行方式。我们的 Kubernetes 实现将每个任务的资源规格同时视为下限和硬性上限：每个容器保证获得指定资源，但一旦超出就会被立即终止。容器运行时通过两个独立参数强制执行资源：保证分配——预先预留的资源——以及容器被终止的硬限制。当这两个值相同时，瞬态峰值没有任何缓冲空间：短暂的内存波动就可能导致本应成功的容器被 OOM-kill（内存溢出终止）。考虑到这一点，Terminal-Bench 的排行榜使用不同的沙箱提供商，其实施更加宽松，允许临时超额分配而不终止容器，以优先保证基础设施稳定性。

这一发现提出了一个更大的问题：资源配置在多大程度上影响评测分数？

为了量化脚手架的影响，我们在六种资源配置下运行 Terminal-Bench 2.0，从严格执行每个任务规格（1x，同时作为下限和上限）到完全无上限。其他条件保持不变：相同的 Claude 模型、相同的测试工具、相同的任务集。

在实验中，成功率随资源余量增加而提高。这主要是由基础设施错误率在每个步骤单调下降驱动的，从严格执行时的 5.8% 降至无上限时的 0.5%。从严格执行到 3 倍余量（5.8% 到 2.1%）的下降在 p < 0.001 水平上显著。余量越大，因超出分配而被终止的容器越少。

从 1x 到 3x，成功分数在噪声范围内波动（p=0.40）。大多数在 1x 时崩溃的任务无论如何都会失败——这是我们在数据中观察到的。智能体进行探索，遇到资源墙，被抢占，但它从未走在正确解决方案的路径上。

然而，从 3x 左右开始，这一趋势发生变化：成功率的上升速度超过基础设施错误的下降速度。

从 3x 到无上限，基础设施错误额外下降 1.6 个百分点，而成功率跃升近 4 个百分点。额外资源使智能体能够尝试仅在资源充足时才有效的方法，例如引入大型依赖、生成昂贵的子进程以及运行内存密集型测试套件。在无上限资源下，相对于 1x 的总提升为 +6 个百分点（p < 0.01）。在边际上，`rstan-to-pystan` 和 `compile-compcert` 等任务在获得内存余量时成功率显著提高。

## 这如何影响测量

在约 3 倍 Terminal-Bench 规格之前，额外资源修复的是基础设施可靠性问题，即瞬态资源峰值。Terminal-Bench 维护者使用的沙箱提供商在后台隐式地做到了这一点；评测变得更稳定，但并未变得更简单。

然而，在 3 倍标记之上，额外资源开始主动帮助智能体解决以前无法解决的问题，这表明限制实际上可以改变评测测量的内容。严格的限制无意中奖励非常高效的策略，而宽松的限制更加宽容，奖励能够更好地利用所有可用资源的智能体。

一个快速编写精简、高效代码的智能体在严格约束下会表现良好。一个使用重量级工具暴力求解的智能体在宽松约束下会表现良好。两者都是值得测试的合理能力，但如果不指定资源配置就将它们合并为单一分数，会使差异和现实世界的泛化能力难以解释。

在 `bn-fit-modify` 这个需要贝叶斯网络拟合的 Terminal-Bench 任务上，一些模型的第一步是安装标准的 Python 数据科学栈：`pandas`、`networkx`、`scikit-learn` 及其所有工具链。在宽松限制下，这行得通。在严格限制下，Pod 在安装过程中就会耗尽内存，此时智能体还没写下一行解决方案代码。存在更精简的策略（仅使用标准库从头实现数学原理），一些模型确实默认采用这种方式。其他模型则不会。不同模型有不同的默认方法，资源配置决定了哪些方法能够成功。

我们在不同的 Anthropic 模型上复现了这一核心发现。效应方向一致，但幅度有所不同。同样的趋势似乎也适用于 Claude 以外的模型，但我们尚未对其进行严格测试。

我们还通过在 SWE-bench 上进行交叉实验，测试了这种模式是否适用于 Terminal-Bench 以外的评测。我们在 227 个问题上改变了总可用内存，最高达到基准的 5 倍，每个问题 10 个样本。同样的效应存在，尽管幅度较小：分数再次随内存单调增加，但在 5x 时仅比 1x 高 1.54 个百分点。SWE-bench 任务的资源密集度较低，因此预期效应较小，但这表明资源分配在那里也不是中性的。

## 其他方差来源

资源分配不是唯一的隐藏变量。在某些配置中，时间限制也开始发挥作用。

原则上，评测设置的每个元素都可能影响最终分数，从集群健康状况到硬件规格，从并发级别甚至到出口带宽。智能体评测本质上是端到端的系统测试，该系统的任何组件都可能成为混淆因素。例如，我们观察到通过率会随一天中的时间波动，这可能是因为 API 延迟随流量模式和事件而变化。我们尚未正式量化这种效应，但它说明了一个更大的观点："模型能力"与"基础设施行为"之间的边界比单一基准测试分数所暗示的要模糊得多。模型提供商可以通过专用硬件使其评测基础设施免受此影响，但外部评估者难以做到同样的事情。

公共基准测试通常旨在测量纯粹的模型能力，但在实践中，它们可能会将其与基础设施特性混淆。有时这可能是可取的，因为它能够对整个技术栈进行端到端测试，但更多时候并非如此。对于旨在公开共享的编程评测，在多个时间、多天运行有助于平均掉噪声。

## 我们的建议

理想情况是在完全相同的硬件条件下运行每个评测——包括运行评测的脚手架和推理栈——这将确保完美的可重复性。然而，这可能并不总是切实可行。

鉴于容器运行时实际强制执行资源的方式——通过保证分配和单独的硬终止阈值——我们建议评测针对每个任务指定这两个参数，而不是单一固定值。单一精确规格将保证分配等同于终止阈值，不留任何余量：我们在 1x 记录到的瞬态内存峰值足以破坏评测稳定性。分离这两个参数可以让容器有足够的呼吸空间避免虚假的 OOM 终止，同时仍然强制执行防止分数膨胀的硬上限。

两者之间的区间应该经过校准，使得下限和上限处的分数落在彼此的噪声范围内。例如，在 Terminal-Bench 2.0 中，在每个任务规格之上设置 3 倍上限，将基础设施错误率降低了约三分之二（5.8% 到 2.1%，p < 0.001），同时保持分数提升适度且完全在噪声范围内（p = 0.40）。这是一个合理的权衡：基础设施混淆因素在很大程度上被中和，而没有消除有意义的资源压力。确切的倍数将因基准测试和任务分布而异，因此应该报告，但经验校准原则是通用的。

## 我们为什么关注

这些发现对评测基础设施之外也有实际影响。基准测试分数越来越多地被用作决策输入，但这种增加的关注（和依赖）并不总是伴随着相应的运行或报告严谨性。按照目前的情况，排行榜上 2 分的领先优势可能反映真正的能力差异，也可能只是反映一个评测运行在更强大的硬件上，甚至在更幸运的时间，或两者兼有。如果没有发布（或标准化）的设置配置，外部人员很难判断，除非相关方付出额外努力在相同条件下重现客观结果。

对于像 Anthropic 这样的实验室，这意味着智能体评测的资源配置应该被视为一等实验变量，以与提示格式或采样温度相同的严谨性进行记录和控制。对于基准测试维护者，发布推荐的资源规格（如 Terminal-Bench 2.0 所做）大有帮助，而指定强制执行方法将消除我们发现的差距。对于任何使用基准测试结果的人来说，核心结论是智能体评测上的小分数差异比报告数字的精度所暗示的带有更多不确定性——特别是因为一些混淆因素根本难以控制。

在资源方法标准化之前，我们的数据表明，在评测配置被记录和匹配之前，低于 3 个百分点的排行榜差异值得怀疑。在 Terminal-Bench 中等资源配置范围内观察到的差异略低于 2 个百分点。朴素的二项式置信区间已经跨越 1-2 个百分点；我们在此记录的基础设施混淆因素叠加在其之上，而非其中。在分配范围的极端，差异达到 6 个百分点。

几分的领先可能标志着真正的能力差距——也可能只是一个更大的虚拟机。
