# Codex 最佳实践

如果你是 Codex 或编码代理（coding agent）的新手，本指南能帮助你更快获得更好的结果。它涵盖了让 Codex 在 [CLI](/codex/cli)、[IDE 扩展](/codex/ide) 和 [Codex app](/codex/app) 上都更高效的核心习惯——从提示与规划，到验证、MCP、技能与自动化。

Codex 的最佳使用方式，不是把它当作一次性的助手，而是像一位你可以长期配置和培养的队友。

一个有用的思考框架是：先准备好正确的任务上下文，用 `AGENTS.md` 承载持久性的指导，按你的工作流配置 Codex，用 MCP 连接外部系统，把重复性工作沉淀为技能，再用自动化让稳定的工作流自动跑起来。

## 初次高效使用：上下文与提示

即使你的提示并不完美，Codex 也已经足够强大，可以直接产出有用的结果。你常常可以把一个难题交给它，用很少的初始设置就拿到不错的产出。清晰的 [提示词](/codex/prompting) 并非获得价值的必要条件，但确实能让结果更稳定——尤其是在大型代码库或高风险任务中。

如果你在大型或复杂的代码仓库中工作，最大的提升来自于给 Codex 正确的任务上下文，以及清晰说明你希望完成的内容。

一个好的默认做法是在提示中包含四件事：

- **目标（Goal）：** 你想改变或构建什么？
- **上下文（Context）：** 哪些文件、目录、文档、示例或错误与该任务相关？你可以用 @ 提及某些文件作为上下文。
- **约束（Constraints）：** Codex 应遵循哪些标准、架构、安全要求或约定？
- **完成条件（Done when）：** 任务完成前应该成立什么，比如测试通过、行为发生改变、或某个 bug 不再复现。

这样能帮助 Codex 保持聚焦、减少臆测，并产出更易评审的成果。

根据任务难度选择推理强度（reasoning level），并测试哪种最适合你的工作流。不同的用户和任务适合的设置各不相同。

- 低（Low）：更快、范围明确的任务
- 中（Medium）或高（High）：更复杂的变更或调试
- 超高（Extra High）：长链路、强代理行为、重度推理的任务

为了更快速地提供上下文，可以尝试在 Codex app 内使用语音听写，直接口述你想让 Codex 做什么，而不用手打。

## 复杂任务先规划

如果任务复杂、含糊或难以描述清楚，可以让 Codex 在开始写代码之前先做规划。

几种行之有效的方法：

**使用 Plan 模式（Plan mode）：** 对大多数用户来说，这是最简单也最有效的选项。Plan 模式让 Codex 在动手实现前先收集上下文、提出澄清问题，并构建更扎实的方案。可通过 `/plan` 或 Shift + Tab 切换。

**让 Codex 反过来采访你：** 如果你有一个粗略的想法但不确定怎么描述好，可以先让 Codex 来反问。让它挑战你的假设，把模糊的想法先打磨成具体方案，再开始写代码。

**使用 PLANS.md 模板：** 对于更进阶的工作流，你可以配置 Codex 遵循 `PLANS.md` 或执行计划（execution plan）模板，用于长链路或多步骤任务。更多细节可参考 [执行计划指南](/cookbook/articles/codex_exec_plans)。

## 用 AGENTS.md 让规范可复用

当一种提示模式被验证有效后，下一步就是停止手工重复它。[AGENTS.md](/codex/guides/agents-md) 正是为此而生的。

可以把 `AGENTS.md` 理解为面向代理的开放式 README。它会自动加载到上下文中，是你和你团队规定 Codex 在仓库中应如何工作的最佳载体。

一份好的 `AGENTS.md` 应当覆盖：

- 仓库结构与重要目录
- 如何运行项目
- 构建、测试与 lint 命令
- 工程约定与 PR 期望
- 约束与禁止事项
- “完成”的定义以及如何验证工作

CLI 中的 `/init` 斜杠命令是在当前目录快速生成一份起步级 `AGENTS.md` 的快捷命令。这是一个很好的起点，但你应当根据团队实际构建、测试、评审和发布代码的方式对其进行编辑。

你可以在不同层级创建 `AGENTS.md`：放在 `~/.codex` 的全局 `AGENTS.md` 用于个人默认设置；放在仓库根目录的 `AGENTS.md` 用于共享规范；放在子目录里的更细粒度文件用于局部规则。如果当前目录附近存在更具体的文件，那份规则优先。

保持实用。一份简短而准确的 `AGENTS.md`，比一份充满空泛规则的长文件更有用。先写基础规范，等到发现重复的错误时再补充新规则。

如果 `AGENTS.md` 变得过大，请保持主文件简洁，并把针对具体任务的内容——例如规划、代码评审或架构说明——引用到独立的 Markdown 文件中。

当 Codex 重复犯同一个错误时，请让它做一次回顾，并据此更新 `AGENTS.md`。这样规范就能始终基于真实摩擦，保持实用。

## 配置 Codex 保持一致性

配置是让 Codex 在不同会话和不同界面之间表现更一致的主要手段之一。例如，你可以为模型选择、推理强度、沙箱模式（sandbox mode）、审批策略（approval policy）、profile（profile）以及 MCP 设置默认值。

一个推荐的起点是：

- 把个人默认设置放在 `~/.codex/config.toml`（在 Codex app 内通过 Settings → Configuration → Open config.toml 打开）
- 把仓库特定行为放在 `.codex/config.toml`
- 命令行覆盖仅用于一次性场景（如果你使用 CLI）

[`config.toml`](/codex/config-basic) 是你定义持久偏好的地方，例如 MCP 服务器、多代理（multi-agent）设置以及功能开关（feature flags）。针对具体 profile 的覆盖则放在独立的 `$CODEX_HOME/profile-name.config.toml` 文件中。

Codex 自带操作系统级沙箱（sandboxing），并提供两个关键开关供你控制。审批模式（approval mode）决定 Codex 在何时就运行某条命令向你征求许可；沙箱模式（sandbox mode）决定 Codex 是否能对目录进行读写，以及代理可以访问哪些文件。

如果你刚开始使用编码代理，请从默认权限开始。默认情况下保持审批与沙箱的严格控制，在明确需要时，再针对受信仓库或特定工作流放宽权限。

请注意，CLI、IDE 和 Codex app 共享同一套配置层。更多内容可参考 [配置示例](/codex/config-sample) 页面。

尽早为你的真实环境配置 Codex。许多质量问题本质上就是配置问题——比如错误的工作目录、缺少写权限、错误的模型默认设置，或者缺少必要的工具与连接器。

## 通过测试与评审提升可靠性

不要止步于让 Codex 做一个改动。必要时请让它编写测试、运行相关检查、确认结果，并在你接受之前对工作进行评审。

Codex 可以替你完成这个循环，但前提是它知道“达标”长什么样。这份指引可以来自提示，也可以来自 `AGENTS.md`。

它可以包括：

- 为改动编写或更新测试
- 运行正确的测试套件
- 检查 lint、格式或类型检查
- 确认最终行为与需求一致
- 评审 diff 中是否存在 bug、回归或风险模式

在 Codex app 中可以切换 diff 面板，就地直接 [评审改动](/codex/app/review)。点击某一行可提供反馈，这些反馈会作为上下文注入到 Codex 的下一轮交互中。

这里一个很有用的选项是斜杠命令 `/review`，它提供几种代码评审方式：

- 基于 base 分支的 PR 风格评审
- 评审未提交的改动
- 评审某个 commit
- 使用自定义评审指引

如果你的团队有一份 `code_review.md` 文件并在 `AGENTS.md` 中引用它，Codex 在评审时也会遵循其中的指引。对于希望在不同仓库和贡献者之间保持评审行为一致性的团队来说，这是一个非常有效的模式。

Codex 不应只生成代码。在合适的指令下，它也能帮助你 **测试、核查与评审**。

如果你使用 GitHub Cloud，你可以为你的 [PR 设置 Codex 代码评审](/codex/integrations/github)。在 OpenAI，Codex 评审 100% 的 PR。你可以开启自动评审，也可以让 Codex 在你 @Codex 时被动触发评审。

## 用 MCP 获取外部上下文

当 Codex 需要的上下文位于仓库之外时，可以使用 MCP。它让 Codex 连接到你已经在使用的工具与系统，你不必再反复把实时信息复制粘贴进提示里。

[Model Context Protocol](/codex/mcp)（简称 MCP）是一个用于把 Codex 连接到外部工具与系统的开放标准。

在以下场景中使用 MCP：

- 所需上下文位于仓库之外
- 数据变化频繁
- 你希望 Codex 使用某个工具，而不是依赖粘贴进去的指令
- 你需要在不同用户或项目之间复用同一套集成

Codex 同时支持带 OAuth 的 STDIO 与 Streamable HTTP 服务器。

在 Codex app 中，前往 Settings → MCP servers 查看自定义和推荐的服务器。通常 Codex 可以帮你安装所需的服务器——你只需要提一句即可。你也可以在 CLI 中使用 `codex mcp add` 命令，填入名称、URL 等信息来添加自定义服务器。

只在工具能真正解锁某个工作流时才添加。不要一开始就把自己用到的所有工具都接进来。先挑选一两个能切实消除你常做的手工循环的工具，再逐步扩展。

## 把重复性工作沉淀为技能

一旦某个工作流变得可重复，就不要再依赖冗长的提示或反复拉扯。请用 [技能（Skill）](/codex/skills) 把指令打包到一份 `SKILL.md` 文件、上下文以及配套逻辑中，让 Codex 始终如一地应用。技能在 CLI、IDE 扩展和 Codex app 上通用。

每个技能应当聚焦于一个职责。先从 2 到 3 个具体用例开始，定义清晰的输入与输出，并在描述中说明技能做什么、何时使用。包含用户真正会说的触发短语。

不要试图一上来就覆盖所有边缘情况。先用一个有代表性的任务跑通，再把该工作流沉淀为技能，并在此基础上持续改进。仅在脚本或附加资源能提升可靠性时再加入它们。

一个有用的经验法则：如果你一直在重复使用同一段提示，或反复纠正同一个工作流，那它就应该被做成一个技能。

技能在以下这类周期性任务中尤其有用：

- 日志分诊（Log triage）
- 发布说明（Release note）起草
- 依据清单进行 PR 评审
- 迁移规划
- 遥测或事件摘要
- 标准化的调试流程

`$skill-creator` 技能是生成技能首个版本的最佳起点。在迭代期间，先把第一版放在本地。等它准备好广泛分享时，再打包为 [插件](/codex/plugins/build)。技能最关键的部分之一是描述：它必须说清楚技能做什么，以及何时使用。

个人技能存放在 `$HOME/.agents/skills`；团队共享的技能可以检入仓库内的 `.agents/skills`。这对新成员入职尤其有帮助。

## 用自动化处理重复工作

当某个工作流稳定下来后，你可以让 Codex 在后台按计划运行它。在 Codex app 中，[自动化（automations）](/codex/app/automations) 允许你为周期性任务选择项目、提示、节奏与执行环境。

当某项任务开始反复出现时，你可以在 Codex app 的 Automations 标签页中创建一条自动化。你可以指定它运行在哪个项目、用哪条提示（也可以调用技能），以及以什么频率运行。你还可以选择该自动化是运行在专用的 git worktree 中，还是运行在你的本地环境。更多内容可参考 [git worktree](/codex/app/worktrees)。

合适的自动化候选包括：

- 汇总最近的 commit
- 扫描潜在 bug
- 起草发布说明
- 检查 CI 失败
- 生成站会（standup）摘要
- 定期运行可复用的分析工作流

一条有用的经验是：技能定义方法，自动化定义节奏。如果某个工作流仍需要大量人工引导，请先把它做成技能；一旦它变得可预测，自动化就能成为倍增器。

把自动化用于反思与维护，而不仅仅是执行。回顾最近的会话，归纳反复出现的摩擦，并持续改进提示、指令或工作流配置。

## 用会话控制组织长任务

Codex 的会话不仅仅是聊天记录。它们是随时间积累上下文、决策与操作的工作线程，因此做好管理对质量影响很大。

Codex app 的界面让线程管理最为轻松，因为你可以置顶线程并创建 worktree。如果你在使用 CLI，这些 [斜杠命令](/codex/cli/slash-commands) 尤其有用：

- `/experimental`：切换实验性功能，并写入你的 `config.toml`
- `/resume`：恢复一次已保存的会话
- `/fork`：新建线程，同时保留原始会话记录
- `/compact`：当线程变长时，对之前的上下文进行摘要压缩。注意 Codex 也会自动压缩会话
- `/agent`：当你并行运行多个代理时，用于在当前激活的代理线程之间切换
- `/theme`：选择语法高亮主题
- `/apps`：在 Codex 中直接使用 ChatGPT apps
- `/status`：查看当前会话状态

保持“一项工作一条线程”。如果工作仍属于同一个问题，留在同一条线程通常更好，因为这样可以保留完整的推理链。只有在任务真正分叉时再 fork。

使用 Codex 的 [子代理（subagent）](/codex/concepts/subagents) 工作流，把范围明确的工作从主线程中卸载出去。让主代理聚焦于核心问题，把探索、测试、分诊等任务交给子代理。

## 常见误区

初次使用 Codex 时，有几个常见误区需要避免：

- 把本应放入 `AGENTS.md` 或技能中的持久性规则塞进提示里
- 没有向代理说明如何运行构建和测试命令，导致它看不到自己的工作成果
- 在多步骤、复杂任务中跳过规划
- 在还不熟悉工作流之前，就赋予 Codex 对你电脑的完全权限
- 不使用 git worktree，就在同一批文件上并行运行多条实时线程
- 任务在手工执行时还不够稳定，就直接把它变成自动化
- 把 Codex 当成必须一步步盯着执行的东西，而不是与你的工作并行使用
- “一个项目一条线程”而非“一个任务一条线程”。这会导致上下文膨胀，长此以往效果会越来越差
